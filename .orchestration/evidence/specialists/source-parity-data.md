## Observations

### Auth contract that migration must preserve

- `apps/api/src/auth/auth.service.ts`: registration and lookup trim/lowercase email; new accounts are always `OWNER`; password hashes use `bcryptjs` cost 12; duplicate email is a conflict; bad credentials are unauthorized. JWT uses `jsonwebtoken`, secret required at startup, configurable `JWT_EXPIRES_IN` default `15m`; verification is followed by database revalidation by ID and email, with the current database role returned (token role is not authoritative).
- `apps/api/src/auth/auth.controller.ts`: session cookie name `alquileres_session`; `HttpOnly`, `Path=/`, `Max-Age=900s`, configurable SameSite (`lax` default; `strict`/`none` supported), Secure in production/explicit setting/SameSite none. Logout clears using matching cookie options. Login/register return `{ user }`.
- `apps/api/src/auth/auth.guard.ts`: accepts `Authorization: Bearer ` before cookie; cookie token is URI-decoded; no token → 401. Role checks are backend-enforced; role failure is also 401 in current service. `AuthService` reloads account on every guard request. Any replacement token/session design must preserve observable expiry, signature rejection, cookie behavior, role freshness, and ADMIN/OWNER isolation or document a justified unresolved incompatibility; do not make JWT claim role authoritative.
- Existing source tests cover normalized email, owner-only registration, hashing, uniqueness conflict, sign/verify, bad token, live-role revalidation and role checks (`auth.service.test.ts`); guard/controller tests are present. They do not establish Workers CPU feasibility for bcrypt cost 12 nor byte-for-byte JWT library compatibility.

### PostgreSQL → D1 data semantics and non-equivalences

- Schema inventory is in `apps/api/prisma/schema.prisma`; ordered source SQL is under `apps/api/prisma/migrations/20260813231707_foundation` through `20260823000000_listing_rental_domain` (10 migrations). Tables: users, listings, listing_images, contact_events, admin_audit_logs. Relations use cascades for owner/listing/contact data, but audit actor and target-owner FKs use RESTRICT. Unique email, unique image object key, unique `(listing_id, position)`, and query indexes are part of behavior.
- PostgreSQL enums must become explicit SQLite text domains (CHECK constraints or equivalent application validation) for Role, ListingStatus, publication/availability status, ContactEventState, PricePeriod, RentalDuration, Currency. Preserve nullability and defaults exactly. PostgreSQL `TIMESTAMP(3)` values need a documented canonical representation and UTC round-trip tests; SQLite has no native timestamp type. `JSONB` audit metadata needs valid-JSON enforcement and JSON round-trip tests; do not coerce to string or discard fields.
- Most importantly, I13 migration intentionally retains legacy `price_per_night` / `max_guests`, drops their NOT NULL, and adds new nullable domain fields. Its SQL explicitly says historical meanings are unknown and must not be inferred. It also sets all `last_confirmed_at` to NULL in a prior migration because old values were not truthful confirmations. A D1 schema/mapping that renames, converts, backfills, or invents these values violates source semantics. This is a strong manual migration checkpoint, not a mechanical Prisma provider swap.
- PostgreSQL migration `20260816000000_listing_review_publication` alters enum types, while later migrations add enums, constraints, and columns. The D1 migration needs fresh-install reproducibility and a version ledger; test schema evolution from each meaningful legacy state, foreign-key enforcement, cascade/restrict behavior, defaults, and uniqueness. `cuid()` and `randomUUID()` key generation currently occur application-side/default behavior; target IDs should be explicit and collision-tested.
- `ListingsService.withListingLock` executes `pg_advisory_xact_lock(hashtextextended(listingId, 0))` inside a transaction. This PostgreSQL locking primitive has no direct D1 equivalent. D1's transaction/serialization semantics must be measured and a race-safe bounded alternative justified for concurrent add/delete/reorder; otherwise H3/H4 remain unresolved. Reorder uses a temporary negative shift (`decrement images.length`) to avoid unique `(listing_id, position)` conflicts, then writes contiguous zero-based positions.

### Image lifecycle and security boundaries

- Source adapter contract (`listing-image.storage.ts`) is bytes by opaque key, get/put, idempotent delete. Keys are `listings/{listingId}/{randomUUID}.{validated extension}`. Database metadata stores object key, original filename, content type, byte size, position, timestamps. Public/API DTOs intentionally omit object key.
- Image input is capped at 5 MiB by default and count at 20; validates file buffer size against supplied size, name safety, declared MIME and basic file signature (JPEG/PNG/WebP). Preserve limits, media validation, metadata, and the source's supported types. `originalName` remains metadata and must not become an object path.
- OWNER image management first verifies listing is owned and in DRAFT/REJECTED; foreign listings are hidden as not found. Add, delete, and reorder are serialized under the per-listing PostgreSQL advisory lock. Reorder requires position in `[0, imageCount)` and writes dense positions. Delete reads current row inside lock, gets bytes, deletes object, deletes DB row and compacts subsequent positions; on metadata failure, attempts restore. Add writes R2 first then D1 metadata; on either storage partial failure or DB failure it best-effort deletes object. Compensation is best effort, so orphan detection/reconciliation is a needed operational consideration, not an atomic guarantee.
- Public bytes are served only when image belongs to a listing with APPROVED and PUBLISHED states (`getPublicImage`); admin image fetch restricts listing owner role to OWNER. The source API sends content type and content length. Public delivery is application-mediated; exposing an R2 public bucket or stable unauthenticated key URL would change the auth/cache boundary unless shown equivalent. Target should keep private bucket and route through Worker or prove equivalent public policy. There is no public-to-private leakage through metadata DTOs.
- Cross-store sequence is not atomic. To preserve existing semantics, validate and authorize before mutation, use deterministic opaque keys, persist metadata after successful R2 put, and compensate on DB failure; delete should retain bytes for compensation before metadata removal as source does. Define recovery for failed compensation (orphan/missing object scan) before claiming complete lifecycle parity.

## Evidence-based conclusion and uncertainty

Conclusion: **UNRESOLVED** for full auth, D1, and R2 parity on this track. Source contracts are now concretely pinned and map-able, and no fundamental model impossibility was found by static inspection. However, static inspection cannot prove Workers bcrypt/JWT CPU/runtime compatibility, D1's exact concurrency behavior, a faithful migration/reconciliation path, or R2 lifecycle delivery/compensation under failures. Do not mark H2/H3/H4 supported on this evidence alone. A D1 implementation must not reproduce PostgreSQL advisory-lock SQL; this is an explicit concurrency design/test obligation. H5 cannot be supported until auth CPU and workload are measured.

Transferable learning: source domain meaning and behavior includes historical non-inference rules, database-backed role freshness, and cross-store compensation; a schema-only comparison misses all three.

## Exact regression cases for orchestrator

1. **Auth parity:** normalized mixed-case/space email; register always OWNER; existing password hash format/cost-12 verification; wrong password and unknown user; JWT issued by source library fixture verifies in target and vice versa if claiming interoperability; expired, malformed, wrong-secret JWT rejected; configured expiry honored; database role change takes effect without re-login; deleted user/email change invalidates token; Bearer precedence over cookie; URI-encoded cookie; cookie exact flags/max-age/SameSite cases; logout clears same attributes; OWNER denied ADMIN endpoint and ADMIN allowed; no auth token → 401. Measure bcrypt cost-12 hash and verify CPU under local Workers `limits.cpu_ms` Free-equivalent cap, including cold/warm results and failure path.
2. **D1 schema/migration:** apply migrations from empty DB deterministically; verify all enum domain checks, nullable legacy/new fields, timestamp precision/UTC, JSON metadata, unique constraints, defaults, FK cascade and RESTRICT; verify I13 legacy price/occupancy values unchanged and `last_confirmed_at` NULL; rerun/ledger behavior and deliberate bad enum/JSON/negative price/nonpositive occupancy failures.
3. **D1 image races:** two concurrent uploads at max-count boundary never exceed limit or collide positions; concurrent delete/reorder/add preserve one dense unique ordering; reorder first↔last, same position, negative, `position == count`, missing image; verify behavior when DB lock/transaction contention occurs. Test every ordering operation with two concurrent synthetic requests on the same listing and on separate listings.
4. **R2 lifecycle/security:** unknown/unowned listing, non-draft status, foreign image ID all return not found and cause zero R2 access; successful put→metadata and returned DTO excludes key; partial put failure and DB insert failure cleanup; delete retrieves bytes, deletes object, metadata deletion/position compaction; DB delete failure restores same bytes/key; restore/delete compensation failure is logged and detectable; reorder changes only metadata; metadata object key never used as authorization; public bytes only for approved+published listing, hidden otherwise; admin read only ADMIN and only OWNER-owned listings; MIME/content length preserved; private bucket/proxy assumptions documented; validate image metadata, unsupported/corrupt MIME signatures and size boundary (exactly max and max+1), unsafe filename.
