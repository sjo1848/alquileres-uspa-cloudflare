# CF-AU-I01-P0P1 — Workers Paid + D1 + R2 cost sensitivity

Observed: 2026-10-12 UTC. This is a sensitivity model, not a bill forecast, quote, spending authorization, or evidence of actual account usage.

## Experiment framing

- **Hypothesis:** a full Cloudflare topology can be budgeted transparently from route counts, D1 scan/write drivers, image operations and Workers Paid CPU/request charges, with an explicit range for unmeasured password-verification CPU.
- **Falsification criterion:** any route is omitted from the modeled Worker request count; D1 rows-read/write formulas disagree with actual query plans/`meta` counters; a billing unit/rate or plan inclusion is stale; or per-invocation CPU/latency makes the bcrypt path infeasible.
- **Setup:** current official Cloudflare pricing/limits pages checked 2026-10-12; three monthly synthetic usage scenarios; explicit per-route read factors, D1 write amplification, stored volume, R2 get/put counts, login and registration CPU sensitivities, and image deletion/reorder lifecycle drivers. The cost calculation is reproducible in `.orchestration/evidence/fixtures/calculate-i01-cost.mjs` and output in `.orchestration/evidence/CF-AU-I01-P0P1-COST-RESULTS.json`.
- **Evidence:** official sources listed below; unit arithmetic generated by the checked-in script. No account or billing panel was accessed.
- **Result:** after adding nonzero registration and image lifecycle work, low/base scenarios estimate USD 5/month across all CPU sensitivities. The deliberately stressed high case estimates USD 23.1467/month at 10 ms assumed provider CPU per auth operation, USD 26.8367 at 100 ms, and USD 47.3367 at 600 ms. The 600 ms value is local bcrypt elapsed-proxy sensitivity only, not provider CPU telemetry.
- **Conclusion:** Workers Paid + D1 + R2 can be budgeted under transparent assumptions, but actual cost is not established. CPU for the source-compatible bcrypt path is the widest high-impact uncertainty. The $5 Workers Paid minimum is not an account spend ceiling; enabling billing or accepting overage remains unauthorized.
- **Transferable learning:** price account and service meters separately, model route work rather than SQL statement counts, and use measured `meta.rows_read`/`rows_written` plus provider CPU metrics before presenting operational estimates as observed.

## Route and data drivers

All counts are invented monthly sensitivity inputs, not product analytics or forecasts. Worker requests include the modeled dynamic route families and API-mediated image GET from public and ADMIN access; static assets are excluded. The source route map is pinned to read-only source `sjo1848/alquileres-uspa@267c531f3e3d5869240894063d3a194fa1f9680b`: `POST /auth/register` (`auth.controller.ts` → `AuthService.registerOwner`, bcryptjs cost 12 + user create); `POST /auth/login` (`validateCredentials`, bcrypt compare); `GET /public/listings/:id/images/:imageId` and `GET /admin/listings/:id/images/:imageId` (R2 `GetObject`); `DELETE /listings/:id/images/:imageId` (`ListingsService.removeImage`, metadata lookup → R2 GetObject → free R2 delete → D1 delete/position compaction); and `PATCH /listings/:id/images/:imageId` (`reorderImage`, load ordered images → reset/reassign positions). The ADMIN image route also reloads the active user through `AuthGuard` and reads owner-role data. The `ownerAdmin` driver represents other OWNER/ADMIN dynamic calls, including listing edits/uploads, and excludes ADMIN image GET and image delete/reorder, which are separately counted. Other public/admin route families remain grouped in their existing drivers. This is a route-cost sensitivity, not an observed workload.

Image-delete drivers assume respectively 2 / 4 / 8 average rows shifted after the removed image. A D1 read factor models one AuthGuard user reload + one owned-draft listing lookup + one image-row lookup + the position-compaction scan (`3 + shifted rows`). The write factor is `5 + 3×shifted rows`: deleting the image row and its four pinned-source index entries (primary key, unique object key, unique listing/position, and separate listing/position index), plus each shifted row and its two position-index entries. Reorder assumes 4 / 6 / 8 average images per listing, `4×image-count + 2` D1 rows read (AuthGuard user + owned-draft listing + ordered load + bulk update match + per-image update lookup + final ordered read), and `6×image-count` metered writes (two rounds of position updates, each charged as one table row plus two index-row mutations). These are transparent planning assumptions, not claimed D1 `meta` measurements. Each image delete includes one R2 `GetObject` Class B read before the free Standard `DeleteObject`; failed-operation compensation re-Puts and retry amplification remain unmodeled. Public image GET assumes 2 D1 rows read (image/listing); ADMIN GET assumes 4 (AuthGuard user revalidation + image/listing/owner-role lookup). The scenario assigns a 95%/5% public/ADMIN traffic mix. Registration source does not issue an explicit user lookup, so its D1 query-read factor is zero; possible engine-level unique-index probe reads are unmeasured and not counted. Registration assumes one user row plus primary-key and unique-email index rows written.

The high scenario deliberately assumes 15,000 scanned catalog rows per call to expose the cost of an unindexed search over a larger listing set; it is not an asserted product cardinality. Its 2M logins make password-guessing volume visible as a cost/availability risk, not an expected demand level. For upper CPU sensitivities, **every modeled login** is assumed to reach bcrypt comparison and every registration to execute one bcryptjs cost-12 hash. The same 10 / 100 / 600 ms assumed provider CPU per auth operation is applied to each login and registration; provider CPU is unmeasured. Unknown-account login skips bcrypt and would use less CPU. Registration volumes are scenario assumptions, not a claim that all registrations succeed. Listing edits/uploads remain D1/R2 subdrivers inside the other OWNER/ADMIN request bucket; image GET/delete/reorder have separate Worker route drivers and do not double count in that bucket.

## CPU sensitivity and modeled totals

The source-compatible bcryptjs cost-12 local Workerd proof's final run observed successful comparisons at 567ms cold and 542ms warm, wrong-password comparisons at 631ms cold and 557ms warm, registration hash at 644ms, and 0ms for an unknown account (which skips bcrypt). Cloudflare bills CPU time, not elapsed duration. The source worker did not expose actual provider CPU metering, so the model uses three clearly marked **assumed provider CPU ms per login or registration** values (10, 100, 600), and uses 5ms/request non-auth in Low/Base and 8ms/request in High. The 600ms input is a conservative illustrative sensitivity near the local elapsed proxy; it is not an exact measurement and not a claim of 600 billed CPU-ms.

|---|---:|---:|---:|

The high 10ms case includes USD 3.09 Worker request overage, USD 2.73 CPU overage, USD 5.3817 D1 row-read overage, USD 1.50 D1 storage, USD 4.50 R2 Class A after rounding uploads to 2M, USD 0.72 R2 Class B after rounding image GETs plus delete prefetch reads to 12M, USD 0.225 R2 storage, and the USD 5 account minimum. The 100ms and 600ms cases have CPU overage of USD 6.42 and USD 26.92 respectively. No D1 write overage occurs in these assumptions. Low/Base remain within included usage at the modeled rates.

## Risks, falsifiers and omissions

- **CPU / latency:** local Workerd does not provide production billed CPU telemetry; the final local benchmark observed successful bcrypt comparisons at 567ms cold and 542ms warm, which are also user-visible latency risks. Falsifier: a provider-side authorized test shows CPU or p95 latency materially differs. Provider test requires a separate paid/remote Human Gate.
- **D1 scans:** catalog's 15k-row high scan and all per-route read factors are assumptions. Falsifier: `EXPLAIN QUERY PLAN` and D1 `meta.rows_read` differ after a future authorized schema/query proof. Full D1 schema/migrations are out of this task.
- **Attack exposure:** login CPU can scale with guesses. The model quantifies monthly volume only; burst concurrency and its throttling/availability impact are not modeled. No rate limit, per-account lockout, challenge, abuse analytics or billing guardrail was demonstrated. A per-request CPU ceiling does not prevent repeated chargeable requests.
- **R2 counts and lifecycle:** no real object sizes, retention, failure compensation, retry behavior, list/head calls or cache behavior are observed. Delete drivers include source read-before-delete GetObject Class B and assume the Standard DeleteObject itself is free. Reorder uses no R2 operation in the source. Cache design must not bypass API authorization or public-state checks.
- **Registration and image churn:** registration success/duplicate mix is not modeled; all registration drivers are treated as successful cost-12 hashes + one insert. Delete/reorder frequencies, image counts shifted, D1 index amplification and query scan counts are assumptions. Full retries, concurrency, lock behavior, cleanup amplification and failed-operation compensation are unresolved; this is cost sensitivity only, not P2 lifecycle/concurrency proof.
- **Shared account consumption:** Worker plan/D1/R2 included allowances may already be used by unrelated account traffic. No live billing account was inspected.
- **Monthly unit rounding:** R2 operations/storage are rounded up in the script; Worker/D1 charges use displayed unit rates and exact excess. A final calculator/account estimate must check any future pricing changes and provider invoices.
- **Tax, domain, third-party messaging/email, paid logging/observability, backup/retention and support plans** are excluded. R2 egress and D1 transfer are documented as free, but this does not make the overall app cost zero.
- **DO not costed into scenario totals:** the optional SQLite DO rates for requests, active duration, rows read/written and stored data are explicitly recorded above and in the calculator output, but the DO cost remains unresolved because usage and a parity-safe actor topology have not been demonstrated. Source uses a PostgreSQL transaction advisory lock; D1 transactional/conditional concurrency safety remains unproven, and adopting DO is a separate architecture plus cost decision.
- **Billing safety:** no hard account-wide spend cap was verified. A malicious request burst or unbounded traffic can increase overage beyond the examples; USD 5 is only a minimum, not a maximum. No purchase, billing enablement or overage acceptance is authorized.
