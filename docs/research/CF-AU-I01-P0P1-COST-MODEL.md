# CF-AU-I01-P0P1 — Workers Paid + D1 + R2 cost sensitivity

Observed: 2026-10-12 UTC. This is a sensitivity model, not a bill forecast, quote, spending authorization, or evidence of actual account usage.

## Experiment framing

- **Hypothesis:** a full Cloudflare topology can be budgeted transparently from route counts, D1 scan/write drivers, image operations and Workers Paid CPU/request charges, with an explicit range for unmeasured password-verification CPU.
- **Falsification criterion:** any route is omitted from the modeled Worker request count; D1 rows-read/write formulas disagree with actual query plans/`meta` counters; a billing unit/rate or plan inclusion is stale; or per-invocation CPU/latency makes the bcrypt path infeasible.
- **Setup:** current official Cloudflare pricing/limits pages checked 2026-10-12; three monthly synthetic usage scenarios; explicit per-route read factors, D1 write amplification, stored volume, R2 get/put counts and login CPU sensitivities. The cost calculation is reproducible in `.orchestration/evidence/fixtures/calculate-i01-cost.mjs` and output in `.orchestration/evidence/CF-AU-I01-P0P1-COST-RESULTS.json`.
- **Evidence:** official sources listed below; unit arithmetic generated by the checked-in script. No account or billing panel was accessed.
- **Result:** low/base scenarios estimate USD 5/month across all CPU sensitivities. The deliberately stressed high case estimates USD 23.0005/month at 10 ms assumed provider CPU per login, USD 26.6005 at 100 ms, and USD 46.6005 at 600 ms. The 600 ms value is local bcrypt elapsed-proxy sensitivity only, not provider CPU telemetry.
- **Conclusion:** Workers Paid + D1 + R2 can be budgeted under transparent assumptions, but actual cost is not established. CPU for the source-compatible bcrypt path is the widest high-impact uncertainty. The $5 Workers Paid minimum is not an account spend ceiling; enabling billing or accepting overage remains unauthorized.
- **Transferable learning:** price account and service meters separately, model route work rather than SQL statement counts, and use measured `meta.rows_read`/`rows_written` plus provider CPU metrics before presenting operational estimates as observed.

The high scenario deliberately assumes 15,000 scanned catalog rows per call to expose the cost of an unindexed search over a larger listing set; it is not an asserted product cardinality. Its 2M logins make password-guessing volume visible as a cost/availability risk, not an expected demand level. For an upper CPU sensitivity, **every modeled login** is assumed to reach the bcrypt comparison path (for example, an existing account with a wrong password). The source returns early for an unknown email and skips bcrypt; that path would use less CPU and is not the costly-login assumption. Edits/uploads are subsets of the OWNER/ADMIN route counts, not additive Worker requests.

## CPU sensitivity and modeled totals

The source-compatible bcryptjs cost-12 local Workerd proof's final run observed successful comparisons at 567ms cold and 542ms warm, wrong-password comparisons at 631ms cold and 557ms warm, and 0ms for an unknown account (which skips bcrypt). Cloudflare bills CPU time, not elapsed duration. The source worker did not expose actual provider CPU metering, so the model uses three clearly marked **assumed provider CPU ms/login** values (10, 100, 600), and uses 5ms/request non-login in Low/Base and 8ms/request in High. The 600ms input is a conservative illustrative sensitivity near the local elapsed proxy; it is not an exact measurement and not a claim of 600 billed CPU-ms.

| Scenario | Assumed CPU/login | Estimated Worker CPU ms/month | Estimated total/month |
|---|---:|---:|---:|
| Low | 10 / 100 / 600 ms | 0.525M / 0.975M / 3.475M | USD 5.00 in each case |
| Base | 10 / 100 / 600 ms | 15.1M / 16.9M / 26.9M | USD 5.00 in each case |
| High | 10 ms | 164M | USD 23.0005 |
| High | 100 ms | 344M | USD 26.6005 |
| High | 600 ms elapsed-proxy sensitivity only | 1,344M | USD 46.6005 |

The high model includes USD 3.00 Worker request overage, USD 5.3755 D1 row-read overage, USD 1.50 D1 storage, USD 4.50 R2 Class A after rounding 1.5M operations to 2M, USD 0.72 R2 Class B after rounding 11.5M to 12M, USD 0.225 R2 storage, the USD 5 account minimum, and the CPU sensitivity charge shown by the script. No D1 write overage occurs in these assumptions. Low/Base remain within included usage at the modeled rates.

## Risks, falsifiers and omissions

- **CPU / latency:** local Workerd does not provide production billed CPU telemetry; the final local benchmark observed successful bcrypt comparisons at 567ms cold and 542ms warm, which are also user-visible latency risks. Falsifier: a provider-side authorized test shows CPU or p95 latency materially differs. Provider test requires a separate paid/remote Human Gate.
- **D1 scans:** catalog's 15k-row high scan and all per-route read factors are assumptions. Falsifier: `EXPLAIN QUERY PLAN` and D1 `meta.rows_read` differ after a future authorized schema/query proof. Full D1 schema/migrations are out of this task.
- **Attack exposure:** login CPU can scale with guesses. The model quantifies monthly volume only; burst concurrency and its throttling/availability impact are not modeled. No rate limit, per-account lockout, challenge, abuse analytics or billing guardrail was demonstrated. A per-request CPU ceiling does not prevent repeated chargeable requests.
- **R2 counts:** no real object sizes, retention, multipart/retry behavior, list/head calls or cache behavior are observed. Class A/B totals are simple count assumptions. Cache design must not bypass API authorization or public-state checks.
- **Shared account consumption:** Worker plan/D1/R2 included allowances may already be used by unrelated account traffic. No live billing account was inspected.
- **Monthly unit rounding:** R2 operations/storage are rounded up in the script; Worker/D1 charges use displayed unit rates and exact excess. A final calculator/account estimate must check any future pricing changes and provider invoices.
- **Tax, domain, third-party messaging/email, paid logging/observability, backup/retention and support plans** are excluded. R2 egress and D1 transfer are documented as free, but this does not make the overall app cost zero.
- **DO omitted from base:** no DO lock or actor model was tested; source uses a PostgreSQL transaction advisory lock. D1 transactional/conditional concurrency safety remains unproven, and adopting DO is a separate architecture plus cost decision.
- **Billing safety:** no hard account-wide spend cap was verified. A malicious request burst or unbounded traffic can increase overage beyond the examples; USD 5 is only a minimum, not a maximum. No purchase, billing enablement or overage acceptance is authorized.
